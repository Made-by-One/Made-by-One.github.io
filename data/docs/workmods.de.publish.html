Release

Veröffentlichen

Veröffentlichen ist ein Pull Request. Du brauchst ein GitHub-Konto; kein Git-Wissen, keine Schreibrechte an der Registry und keinen Server.

  1. Der Client packt den Mod-Ordner als ZIP (Wurzel = der Ordner selbst, ohne Wrapper) und berechnet den SHA-256.
  2. Alle Dateien sowie icon.png / banner.png werden in dein Mod-Repository committet.
  3. Ein Release v<version> entsteht, <modId>.zip wird angehängt.
  4. Ein Pull Request fügt submissions/<game_id>/<mod_id>.json mit Metadaten, Download-URL, Digest und deinem Login hinzu.
  5. Validate Submission prüft Pfad, ID, Version, Hash und Release-URL. Ein Maintainer sieht es sich an und merged.
  6. Rebuild Mod Registry erzeugt registry.json aus allen Einreichungen neu. Spieler sehen den Mod nach der nächsten Katalogaktualisierung.

Versionen und Updates

  • Versionen sind freier Text ohne Leerzeichen und Schrägstriche: 1.0.0, 1.2.0, 2.0.0-beta.1. Das Tag ist immer v<version>.
  • Erneutes Veröffentlichen derselben Version nutzt das Release weiter und ersetzt dessen Asset.
  • Zum Aktualisieren den Mod bearbeiten, Version erhöhen und veröffentlichen — der Pull Request aktualisiert dieselbe Einreichungsdatei, Spieler behalten einen Eintrag. Schließe vorher einen noch offenen Pull Request zu diesem Mod.
  • Unpublish öffnet einen Pull Request, der die Einreichungsdatei löscht. Repository, Dateien und Releases bleiben online, bestehende Spieler behalten ihre lokale Kopie.

Grenzen

GrenzeWert
Einzelne Datei über die GitHub Contents APIDeutlich unter 100 MB — die API ist kein CDN
Release-ZIPBis 2 GB
Mod-ID[a-z0-9][a-z0-9._-]{1,63}
TagsListe mit höchstens 20 kurzen Zeichenketten
Prüfsumme64 Hex-Zeichen in Kleinbuchstaben, der Client prüft sie nach dem Download

Vor dem Veröffentlichen: game_id passt exakt zum Spiel, Bundles sind für die richtige Plattform gebaut, die Version ist erhöht und die Mod-ID unverändert, der Mod wurde lokal getestet, und im Ordner liegen keine Geheimnisse oder unlizenzierten Inhalte.
